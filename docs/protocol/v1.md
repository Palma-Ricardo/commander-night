# Commander Night — Browser Protocol v1 (draft)

**Date:** 2026-07-15 · **Status:** DRAFT for review · **Scope:** browser ⇄ bridge over WebSocket/JSON.
The bridge ⇄ XMage side is fixed by XMage (Java serialization, see
`docs/plans/2026-07-15-xmage-bridge-spike.md`); this document defines the *other* side — the
protocol our TypeScript client speaks. Schema notation is TypeScript; it is intended to become the
shared `protocol.ts` types file verbatim.

## 1. Goals

1. **Semantic, not a mirror.** Messages express MTG concepts (zones, prompts, priority), never
   XMage view classes. XMage stays a swappable backend; a future TS engine would implement this
   same protocol.
2. **Thin client.** The client renders what the server says and never infers rules. Every clickable
   affordance is explicitly delivered (prompt candidates, playable actions). No client-side card
   database: card identity is `set` + `collectorNumber`, images resolved client-side (Scryfall).
3. **Efficient.** The spike showed XMage's raw stream is ~183 MB/seat/game; target is low
   single-digit MB before WS compression.
4. **Interaction-complete for Commander FFA.** Every XMage dialog reachable in a 4-player
   Commander game maps to a prompt kind (§8).

**Non-goals (v1):** tournaments, drafts, replays, sideboarding, hand-reveal permission flows,
spectator chat moderation, in-browser deck *building* (submission is text).

## 2. Empirical basis (spike log `bridge/logs/spike-1784169224029.jsonl`)

One seat's view of a full 46-turn 4-player AI Commander game:

- 2,465 callbacks, 183 MB JSON. Per-line size p50 85 KB, p90 120 KB, max 148 KB.
- 1,908 callbacks are **full GameView snapshots** (`GAME_UPDATE` + `GAME_UPDATE_AND_INFORM`).
  Consecutive snapshots differ by **< 1 %** (measured: 40 changed lines out of ~5,100 —
  `hasPriority`, timers, `gameCycle`).
- 1,330 callbacks carry a status string ("Upkeep - Waiting for ai_1") that is **100 % derivable**
  from state (`turn.step` + `turn.priorityPlayerId`). Dropped entirely; the client renders its own
  status line.
- Card views carry ~70 fields, most render-oriented for Swing (`frameStyle`, `artRect`,
  `manaCostLeftStr`, `imageFileName`, …). Trimmed to ~20 semantic fields.
- Prompt-type callbacks are rare (276 total) and small once the embedded GameView is stripped.
- GameView is **already per-seat filtered by the server** (`myHand`, hidden opponent hands), so
  privacy is inherited: the bridge holds one XMage session per human seat and fans out one
  WebSocket per seat. The bridge adds no privacy logic of its own.

Consequences: snapshot + diff on a **trimmed** model, prompts as first-class small messages, drop
everything derivable or render-only.

## 3. Transport and envelope

- One WebSocket per browser session (`wss://<bridge>/ws`), JSON text frames, one message per
  frame, `permessage-deflate` enabled.
- Every message has a `t` (type) discriminator: `{ "t": "game.patch", ... }`.
- **Commands** (client → server) carry a client-generated `id`; the server always answers with
  `ack` or `error` referencing it via `re`. **Events** (server → client) carry `seq`, a
  bridge-owned counter monotonic per game per seat, shared by all `game.*` events.
- Command `id`s MUST be unique per session **across reconnects** — the idempotency window (§14)
  is per session token, precisely so a retry after a dropped ack still deduplicates. A client
  that restarts a `c1, c2, …` counter on page reload while resuming a token would receive
  stale recorded replies; use random ids or a persisted counter.
- Timestamps are epoch millis. All IDs are opaque strings (XMage UUIDs pass through unchanged).
- Unknown fields and unknown `t` values MUST be ignored (forward compatibility).

```ts
type Id = string;

interface Command { t: string; id: string }          // client → server
interface Event   { t: string; seq?: number }        // server → client
interface Ack     { t: 'ack';   re: string }
interface Err     { t: 'error'; re?: string; code: ErrorCode; message: string; fatal?: boolean }
```

## 4. Session layer

```ts
// client → server, first message on every connection
interface Hello {
  t: 'session.hello';
  id: string;
  v: 1;                       // protocol major version; server rejects mismatch
  token?: string;             // session token from a prior welcome (§16.6); omit on first connect
  resume?: { gameId: Id; lastSeq: number };
}

// server → client
interface Welcome {
  t: 'session.welcome';
  re: string;
  v: 1;
  userId: Id;
  token?: string;             // fresh sessions only: bridge-minted session token — persist
                              // (localStorage) and present on every later hello (§16.6)
  role: 'player' | 'spectator';
  resumed: boolean;           // true → keyframe + open prompt follow immediately
}
```

Resume semantics (§14): the bridge keeps the XMage session alive independently of the WebSocket —
a dropped browser connection does not cost the seat. On resume the bridge always sends a fresh
`game.state` keyframe, the pending `game.prompt` if any, and the last 50 `game.log` entries;
`lastSeq` is used only to suppress duplicate log lines.

## 5. Lobby layer (v1 minimal — friends' night, not a public server)

Deliberately thin; the bridge owns table setup against XMage (`createTable`/`joinTable`/
`startMatch` per the spike recipe).

```ts
// commands
{ t:'lobby.create'; id; format:'commander-ffa'; name?: string }        // → ack, then a lobby.state
                                                                       // event carries the code
{ t:'lobby.join';   id; code: string; displayName: string }
{ t:'lobby.deck';   id; format:'dck'|'list'; content: string }         // text upload; bridge parses
{ t:'lobby.ready';  id; ready: boolean }
{ t:'lobby.start';  id; fillAI?: boolean }                             // host only; fillAI:true
                                                                       // fills empty seats with
                                                                       // server AI + sample decks

// event — full small snapshot on every change (no diffing needed at this size)
interface LobbyState {
  t: 'lobby.state';
  code: string;
  hostUserId: Id;
  seats: { userId: Id; name: string; deck?: { valid: boolean; commander?: string[];
           cards: number; problems?: string[] }; ready: boolean }[];
}
```

`lobby.deck` acks with the parse result (commander names, card count) or errors with per-line
diagnostics. The spike proved `.dck` parses trivially; a plain "1 Card Name" list format is ours
to define.

`lobby.join` remains valid after the game has started: a `displayName` matching a seated player
(case-insensitive) re-binds that seat to the caller's session token — the lost-token recovery
path (§16.6) — and the §14 resume sequence follows. A non-matching name on a running game →
`error LOBBY_STATE`. The re-bound session **adopts the seat's `userId`** (the one in
`lobby.state` and game log `playerId`s); the `userId` from the caller's fresh `welcome` is
abandoned.

A **started lobby no longer holds its members**: once the game is running (or over), its players
may `lobby.create` or `lobby.join` a fresh lobby — that is the whole rematch flow (§11). The
old lobby stays addressable by code only for the recovery-join path above. v1 does not pre-fill
rematch seats; players re-join and re-submit decks (clients hold the deck text).

## 6. Game state model

The document below is what keyframes carry and what patches mutate. Design rules applied to
XMage's GameView:

- **Maps → ordered arrays.** XMage sends zones as ordered maps keyed by UUID; we send arrays
  (order is meaningful in MTG: graveyard order, stack order).
- **Render hints dropped** (`frameStyle`, `artRect`, `imageFileName`, `cardIcons`, mana cost
  halves, …). Card identity `set`+`number` is enough for client-side image resolution.
- **Interaction hints lifted out of state.** XMage bakes `isChoosable`/`isSelected`/
  `playableStats` into every card view, which both bloats cards and churns snapshots during
  prompts. We move all of that into the active `game.prompt` (§8). State stays interaction-free.
- **Derivable strings dropped** (the 1,330 status lines, player-colored HTML).
- **Commander first-class.** Command zone, per-opponent commander damage, and cast count (tax) are
  structured fields. NB: XMage exposes commander damage only as HTML injected into the
  commander's info text (`CommanderInfoWatcher.addCardInfoToCommander`, verified in source); the
  bridge scrapes it with a version-pinned regex and fixture tests (§16).

```ts
type Color = 'W'|'U'|'B'|'R'|'G';
type Phase = 'BEGINNING'|'PRECOMBAT_MAIN'|'COMBAT'|'POSTCOMBAT_MAIN'|'END';
type Step  = 'UNTAP'|'UPKEEP'|'DRAW'|'PRE_MAIN'|'BEGIN_COMBAT'|'DECLARE_ATTACKERS'
           | 'DECLARE_BLOCKERS'|'FIRST_COMBAT_DAMAGE'|'COMBAT_DAMAGE'|'END_COMBAT'
           | 'POST_MAIN'|'END_TURN'|'CLEANUP';

interface Card {
  id: Id;
  name: string;
  set: string;                 // expansion set code
  number: string;              // collector number  → set+number = image lookup key
  manaCost?: string;           // "{2}{U}{U}"
  manaValue: number;
  types: string[];             // CREATURE, INSTANT, …
  subtypes: string[];
  supertypes: string[];
  colors: Color[];
  text: string[];              // rules lines, XMage HTML stripped to plain text
  power?: string; toughness?: string;
  loyalty?: string; defense?: string;
  counters?: { name: string; count: number }[];
  token?: boolean;
  faceDown?: boolean;          // face-down anywhere (exile, library plays, …)
}

interface Permanent extends Card {
  controllerId: Id;
  tapped: boolean;
  flipped?: boolean;
  transformed?: boolean;
  // CONFIRMED live: the controller's view of their own face-down permanent keeps its
  // identity (name "Morph: Hooded Hydra", morphed flag, morph rules text); opponents
  // receive a server-redacted 2/2 with no name. The bridge passes each seat's view
  // through unchanged — privacy is XMage's job, not ours.
  morph?: 'morphed'|'manifested'|'disguised'|'cloaked';
  damage?: number;
  summoningSick?: boolean;
  attachments?: Id[];          // auras/equipment attached to this
  attachedTo?: Id;             // permanent or player this is attached to
  copy?: boolean;
}

interface StackItem {
  id: Id;
  controllerId?: Id;           // absent when XMage's view doesn't expose it: spell views carry
                               // no controller UUID (only abilities resolve via their source's
                               // battlefield); revisit if the client needs it (§16)
  kind: 'spell' | 'ability';
  card?: Card;                 // the spell, or the ability's source card for context
  text: string[];              // what will happen (ability rules text)
  targets?: Id[];              // chosen targets (object or player ids)
}

interface CommandObject extends Card {
  kind: 'commander' | 'emblem' | 'plane' | 'dungeon';
  castCount?: number;          // commander tax = 2 × castCount
}

interface Player {
  id: Id;
  name: string;
  human: boolean;
  life: number;
  counters?: { name: string; count: number }[];   // poison, energy, experience, …
  manaPool: { W:number; U:number; B:number; R:number; G:number; C:number };
  librarySize: number;
  handSize: number;
  battlefield: Permanent[];
  graveyard: Card[];           // ordered, newest last
  exile: Card[];
  commandZone: CommandObject[];
  commanderDamage?: { fromCommanderId: Id; amount: number }[];
  flags?: { monarch?: boolean; initiative?: boolean; left?: boolean; dead?: boolean };
  timer?: { remainingSecs: number; active: boolean };   // absent when clocks disabled
}

interface CombatGroup {
  attackerIds: Id[];
  defenderId: Id;              // player, planeswalker, or battle
  blockerIds: Id[];
  blocked: boolean;
}

interface GameState {
  gameId: Id;
  status: 'active' | 'over';
  rollbackTurnsAllowed: boolean;   // table option (GameView.isRollbackTurnsAllowed — constant
                                   // for a game); gates game.action requestRollback (§9).
                                   // Added 2026-07-18 (pre-client, still additive).
  turn: {
    n: number;
    // phase/step/activePlayerId are ABSENT during the pre-game mulligan window:
    // XMage's view carries no turn structure until the first untap (observed
    // live 2026-07-18; corpus: game.state.mulligan.json). The §2-derived status
    // line falls back to "Mulligans" while they are absent.
    phase?: Phase;
    step?: Step;
    activePlayerId?: Id;
    priorityPlayerId?: Id;
  };
  players: Player[];           // seat order; includes me
  stack: StackItem[];          // bottom → top
  combat?: CombatGroup[];
  revealed?: { name: string; cards: Card[] }[];   // shared reveal windows
  lookedAt?: { name: string; cards: Card[] }[];   // private to this seat
  me: {                                           // private zone; spectators: omitted
    playerId: Id;
    hand: Card[];
    // The active §9 skip; absent = none. At most one is ever active: 1.4.60
    // PlayerImpl.sendPlayerAction resets every skip flag before setting any.
    // Cleared server-side when the skip completes or is interrupted (arrives as a
    // normal patch). NB skip:'stack' on an empty stack is an XMage no-op — the
    // action is acked but the field never appears. Added 2026-07-18.
    skip?: 'stack'|'endOfTurn'|'nextMain'|'myNextTurn'|'endStepBeforeMyTurn';
  };
}
```

## 7. State synchronisation: keyframe + patch

```ts
interface StateKeyframe { t:'game.state'; seq: number; gameId: Id; state: GameState }
interface StatePatch    { t:'game.patch'; seq: number; gameId: Id;
                          base: number;                  // seq the ops apply to
                          ops: JsonPatchOp[] }           // RFC 6902, paths into GameState
{ t:'game.resync'; id; gameId: Id }                      // client → server: send me a keyframe
```

- The bridge maintains the canonical trimmed `GameState` per seat, translates each XMage snapshot
  into it, and emits the RFC 6902 diff between consecutive trimmed states. Empty diffs (snapshots
  that only changed dropped fields, e.g. timer millis) emit nothing.
- Keyframes are sent: on game start (`seq` per-game from 0), on (re)connect, on `game.resync`, and
  after every 100th consecutive patch as a self-healing backstop. The backstop keyframe *follows*
  that patch at the next `seq`, carrying the same tree the patch stream produces — so a client
  that verifies its locally-patched tree against the keyframe (client design §6) checks for an
  exact match, never modulo an unsent diff.
- WebSocket delivery is ordered and reliable, so `base` is an assertion, not a sync mechanism: if
  `base ≠ lastAppliedSeq`, the client stops applying and sends `game.resync`.
- Debug escape hatch: `session.hello` may set `stateMode:'keyframes'` to receive full keyframes
  instead of patches (slow, simple, great for client development).

Why RFC 6902 rather than semantic events: patches are mechanical to produce (tree diff) and apply
(fast-json-patch), and correctness never depends on interpreting game semantics. Deriving *"card X
moved hand → battlefield"* events from XMage snapshots is heuristic (XMage assigns a **new UUID
when an object changes zone** — MTG "new object" semantics), so semantic move events are deferred;
the client can animate from patch paths (`remove` from one zone + `add` in another within one
patch) and from the log. Revisit after the client exists (§16).

Measured sizes (2026-07-16, jq prototype of the §6 trim over real coverage-game snapshots): the
*largest* GameView of a 39-turn game (turn 32, 4 crowded battlefields) trims from 192 KB to
31 KB (6.2×), and to 8.4 KB gzipped (≈ what permessage-deflate achieves on the wire) vs 18.4 KB
for the raw view. Typical patches < 1 KB. Whole game ≈ 1–3 MB/seat before compression (vs
169–191 MB raw across observed games).

## 8. Prompts (server asks) and answers

XMage's eleven dialog callbacks normalize to one `game.prompt` event with a `kind` union. Rules:

- **At most one prompt is pending per seat.** Every prompt has a bridge-issued monotonic
  `promptId`. A new prompt implicitly supersedes the previous one; the bridge also sends
  `game.promptDone` for the superseded prompt so the UI can dismiss cleanly.
- **Answers are fenced by `promptId`.** XMage's answer channel is positional (`sendPlayer*`
  answers "the current question"), so the bridge rejects any `game.answer` whose `promptId` isn't
  the pending one (`error PROMPT_STALE`). This prevents a late click answering the wrong question.
- Prompt messages are plain text (bridge strips XMage's `<font>` HTML).
- All selectable-object hints live here, not in state: `candidates`, `playable`, `selected`.

```ts
interface PromptBase { t:'game.prompt'; seq: number; gameId: Id;
                       promptId: number; message: string }

type Prompt = PromptBase & (
  // GAME_ASK — yes/no
  | { kind:'confirm'; yesText?: string; noText?: string }

  // GAME_SELECT — you have priority, or a combat declaration (see `combat`).
  // playable comes from GameView.canPlayObjects; actions keep XMage's category
  // (mana | play | cast | ability) so the UI can highlight real actions without
  // treating bare mana taps as things to do — conflating them is exactly how the
  // phase-2 spike wedged itself (tap land → float mana → "Pass anyway?" loop).
  //
  // combat present ⇔ the ask is "Select attackers" / "Select blockers"
  // (HumanPlayer rides the toggleable creature UUIDs in the options map —
  // possibleAttackers / possibleBlockers). This ask is NOT a cast window:
  // XMage accepts nothing but creature toggles on it, so `playable` is
  // always {} when `combat` is present. One toggle per round trip, like
  // payMana: {type:'object'} declares a `candidates` creature into combat or
  // withdraws a `declared` one (withdrawal only while the stack is empty —
  // XMage ignores it otherwise), and the server re-prompts with the updated
  // lists. Attacking a multi-defender board: after a toggle-in, a follow-up
  // chooseTargets ("Select defender") picks whom that creature attacks.
  // `special` is XMage's shortcut button label when offered ("All attack" —
  // attackers only, never sent with an empty candidate list); answered with
  // {type:'option', key:'special'}. Done declaring = {type:'confirm'} with
  // EITHER value (XMage checks only that a boolean arrived — the pacifist
  // pass {confirm,false} auto-runners send is already a legal "declare
  // nothing") or {type:'cancel'}. If the declaration is rules-invalid (a
  // must-attack creature stayed home), XMage informs and re-asks.
  | { kind:'priority';
      playable: Record<Id, { kind:'mana'|'play'|'cast'|'ability'; text: string }[]>;
      canPass: true;
      combat?: { role:'attackers'|'blockers';
                 candidates: Id[];      // may be toggled into combat
                 declared: Id[];        // yours already in combat (toggle out)
                 special?: string } }   // shortcut button label, e.g. "All attack"

  // GAME_TARGET / GAME_SELECT with targets — pick objects/players.
  // Also carries XMage's amount-target flows: pile BUILDING ("Select cards to put in
  // the first pile (selected 0 of 3)") and counter/damage DISTRIBUTION ("Select target
  // creatures (selected 1 of 4) to distribute 4 counters"; equal split is implicit when
  // targets == amount — GET_MULTI_AMOUNT only fires for the fewer-targets-than-points
  // case). progress {chosen, of} is parsed from the message so the UI can show a counter.
  | { kind:'chooseTargets'; candidates: Id[]; min: number; max: number;
      required: boolean; zone?: string;
      progress?: { chosen: number; of: number };
      cards?: Card[] }        // full views when candidates aren't in visible state (e.g. discard from hand piles)

  // GAME_CHOOSE_ABILITY — which ability/mode of a source
  | { kind:'chooseAbility'; sourceId?: Id; options: { id: Id; text: string }[] }

  // GAME_CHOOSE_CHOICE — pick one string option (modes, colors, numbers-as-choices, …).
  // XMage's sub-message (dialog subtitle) is folded into `message`. `required:false`
  // means the choice may be declined with {type:'cancel'}. XMage's "remember answer"
  // special mode (a '#'-prefixed auto-answer memory, source: HumanPlayer
  // replacementEffectChoice) is a client-side convenience v1 does not expose.
  | { kind:'chooseOption'; options: { key: string; text: string }[]; required?: boolean }

  // GAME_CHOOSE_PILE — CONFIRMED live (Fact or Fiction): cardsView1/cardsView2 are
  // the piles (either may be empty), message e.g. "Choose a pile to put into hand.".
  // NB pile *building* (Epiphany-style, where we separate) arrives as chooseTargets
  // with progress in the message ("Select cards to put in the first pile (selected
  // 0 of 3)") — no separate prompt kind needed.
  | { kind:'choosePile'; piles: [Card[], Card[]] }

  // GAME_PLAY_MANA — pay a cost (only surfaces when auto-payment can't resolve it).
  // CONFIRMED (2026-07-16 coverage runs, 577 samples): options.queryType="PLAY_MANA",
  // remaining cost is the message prefix (incl. Phyrexian "{B/P}"), sources are
  // exactly gameView.canPlayObjects. Answered live via all three channels:
  // source click (UUID), pool spend (ManaType), cancel (Boolean false).
  // Caveat (observed live 2026-07-17): sources may include objects that cannot
  // contribute to the remaining cost — XMage then re-asks, identical, without
  // tapping anything. Clients must not assume a source click progresses the
  // payment (progress ⇔ the remaining cost in the re-ask shrank).
  | { kind:'payMana'; remaining: string;          // e.g. "{1}{U}", "{1}{B/P}{B/P}"
      sources?: Id[]; canCancel: boolean }

  // GAME_GET_AMOUNT — announce X / pick a number.
  // CONFIRMED: message "Announce the value for {X} …", min 0, max Integer.MAX_VALUE —
  // the bridge passes max through; the client clamps its input UI to something sane.
  // The answer is required: GAME_GET_AMOUNT has no decline channel (XMage re-asks
  // forever), so {type:'cancel'} is rejected with INVALID_ANSWER.
  // X flow is announce (this) → normal payMana prompts. GAME_PLAY_XMANA has no
  // callers in the 1.4.60 server source (dead code); if an upgrade revives it, the
  // bridge relays it as a `confirm` (the Swing client renders it as one).
  | { kind:'chooseAmount'; min: number; max: number }

  // GAME_GET_MULTI_AMOUNT — split a total across rows (damage division, …).
  // Source-verified against 1.4.60, never observed live (§16.1): XMage sends a list
  // of row messages plus overall totalMin/totalMax and per-row bounds. Rows are
  // positional with no server ids — `id` is a bridge-synthesized row index
  // ("0", "1", …), valid only within this prompt. Constraint: min ≤ Σ amounts ≤ total,
  // with each row inside its own [min, max] when present.
  | { kind:'distribute'; total: number; min: number;
      among: { id: Id; label: string;
               min?: number; max?: number;      // per-row bounds when XMage sends them
               suggested?: number }[];          // XMage's default split
      canCancel?: boolean }

  // USER_REQUEST_DIALOG — meta requests (rollback permission, concede confirmation, …).
  // requestKey is the dialog title (XMage sends no machine key). Option keys are
  // XMage PlayerAction enum names (stable within the pinned version, e.g.
  // "ADD_PERMISSION_TO_ROLLBACK_TURN"), or "dismiss" for a button that only closes
  // the dialog; answered with {type:'option'}.
  | { kind:'playerRequest'; requestKey: string; options: { key: string; text: string }[] }
);

interface PromptDone { t:'game.promptDone'; seq: number; gameId: Id;
                       promptId: number; reason:'answered'|'superseded'|'gameOver' }

// client → server
interface Answer {
  t: 'game.answer'; id: string; gameId: Id; promptId: number;
  answer:
    | { type:'confirm';  value: boolean }        // confirm; also priority pass = {confirm,false}
    | { type:'object';   objectId: Id }          // act on / target / mana source / ability id
    | { type:'objects';  objectIds: Id[] }       // multi-target submit (bridge feeds XMage one at a time)
    | { type:'number';   value: number }
    | { type:'option';   key: string }
    | { type:'pile';     index: 0 | 1 }
    | { type:'mana';     color: Color | 'C' }    // pay from pool
    | { type:'distribution'; amounts: { id: Id; amount: number }[] }
    | { type:'cancel' };
}
```

The mapping from each answer type to XMage's six answer primitives
(`sendPlayerBoolean/UUID/Integer/String/ManaType/Action`) is the bridge's job — table in §15.
Multi-target selection (`min`/`max` > 1) is submitted whole by the client; the bridge replays it
to XMage as individual UUID sends, since XMage collects targets one at a time.

`chooseTargets` may equally be answered **one pick at a time** with `{type:'object'}`: the server
then re-prompts with advanced `progress` (the old prompt is superseded) until the selection is
complete — the same per-round-trip shape `payMana` uses. While picking incrementally,
`{type:'confirm', value:true}` means *done with the targets chosen so far* (valid once
`progress.chosen ≥ min`), and `{type:'confirm', value:false}` or `{type:'cancel'}` declines an
optional selection (`required:false` or `min:0`). Clients can rely on either style; a submitted
`{type:'objects'}` whole-set remains the recommended UX for `max > 1`.

Combat declaration (`priority` with `combat`) is per-round-trip **only**: XMage collects one
toggle at a time and re-fires the ask after each, and these asks carry no `selected k of n`
progress for the bridge's replay matcher to key on — so `{type:'objects'}` is rejected there.
The re-fired ask arrives as a fresh prompt (the previous one is superseded) with `candidates`
and `declared` reflecting the toggle just made.

## 9. Player-initiated actions (no prompt required)

```ts
interface GameAction {
  t:'game.action'; id: string; gameId: Id;
  action:
    | { kind:'concede' }
    | { kind:'skip'; mode:'stack'|'endOfTurn'|'nextMain'|'myNextTurn'
                    |'endStepBeforeMyTurn'|'cancel' }     // maps to PASS_PRIORITY_*
    | { kind:'requestRollback'; turns: number }           // gated by GameState.rollbackTurnsAllowed (§6)
    | { kind:'autoMana'; enabled: boolean }               // MANA_AUTO_PAYMENT_ON/OFF
    | { kind:'triggerOrder'; mode:'reset' };              // v1: reset only
}
```

Skip state is reflected only for `me`, as `me.skip` (§6) — own skip state matters to the UI;
opponents' (AIs skip constantly) would only churn patches, so it is trimmed. Source-verified
2026-07-18: `PlayerView` carries six typed skip flags; the five settable through this protocol
map 1:1 (`stack`→`passedUntilStackResolved`, `endOfTurn`→`passedUntilEndOfTurn`,
`nextMain`→`passedUntilNextMain`, `myNextTurn`→`passedAllTurns`,
`endStepBeforeMyTurn`→`passedUntilEndStepBeforeMyTurn`); XMage's remaining two (F4/F6 turn
variants) are unreachable through v1, so they can never be set on a bridge seat. Rollback
requests surface to other players as `playerRequest` prompts.

## 10. Log and chat

```ts
interface LogEntry { t:'game.log'; seq: number; gameId: Id; ts: number;
                     kind:'game'|'chat'|'status'|'error'|'personal';
                     turn?: string;                       // XMage turnInfo, e.g. "T2.M1"
                     text: string;                        // plain text, HTML stripped
                     refs?: { objectId: Id; name: string }[];  // cards mentioned in the line
                     playerId?: Id }                      // speaker / subject when known
{ t:'chat.send'; id: string; gameId: Id; text: string }   // client → server
```

`chat.send` relays the text into the game chat and acks; the line comes back to every seat as a
`game.log` with `kind:'chat'` (the sender included — the client renders only the echo, never a
local copy). `text` is plain text, max 500 chars after trimming (`BAD_MESSAGE` beyond, empty
after trim → `BAD_MESSAGE`). Valid from game start until post-game teardown (§14).

`CHATMESSAGE` shape CONFIRMED (2026-07-16, 1,100+ samples): `{username, time, turnInfo: "T2.M1",
message, color, messageType: 'GAME'|'STATUS'|...}`. The HTML `message` embeds
`object_id='<uuid>'` attributes on every card reference — the bridge extracts those into `refs`
so the client can link/hover log lines to cards. `color: ORANGE` marks turn/match-structure
announcements (derivable from state → dropped); `BLACK` is the real game log.
`GAME_INFORM_PERSONAL` → `kind:'personal'` (only this seat sees it); `GAME_ERROR` →
`kind:'error'` plus an `error` message.

## 11. Game end

```ts
interface GameOver { t:'game.over'; seq: number; gameId: Id;
                     winnerPlayerIds: Id[];
                     reason: string;                      // human-readable, from XMage
                     finalState: true }                   // a final keyframe precedes this event
```

Built from `GAME_OVER` + `END_GAME_INFO`. The connection stays open (post-game chat, rematch via
lobby).

## 12. Errors

```ts
type ErrorCode =
  | 'UNSUPPORTED_VERSION' | 'AUTH_FAILED' | 'RESUME_FAILED'
  | 'BAD_MESSAGE'         | 'UNKNOWN_GAME'
  | 'PROMPT_STALE'        | 'INVALID_ANSWER'
  | 'DECK_INVALID'        | 'LOBBY_STATE'
  | 'UPSTREAM_ERROR';     // XMage session failure; fatal:true → seat lost
```

Non-fatal errors never close the socket. `fatal:true` means the seat is unrecoverable on this
connection (client should return to lobby).

## 13. Versioning

- Single protocol version integer, negotiated in `hello`/`welcome`; mismatch → `UNSUPPORTED_VERSION`.
- Within a major version, changes are additive only (new optional fields, new prompt kinds, new
  event types). Clients ignore what they don't know; a client seeing an unknown *prompt kind* shows
  a generic "answer in text" fallback… which cannot work for all kinds, so prompt kinds are
  **frozen within a major**: adding one bumps the major.
- The bridge version-pins XMage (currently 1.4.60); XMage upgrades are bridge-internal as long as
  the trimmed model translates.

## 14. Reconnect semantics

- Bridge ↔ XMage session lifetime is decoupled from the WebSocket: a browser refresh, phone lock,
  or network blip does not touch the XMage seat (bridge keeps `session.ping()` alive).
- On reconnect: `hello{resume}` → `welcome{resumed:true}` → `game.state` keyframe → pending
  `game.prompt` (if any) → recent `game.log` backfill (entries with `seq > lastSeq`, capped at 50).
  The re-emitted prompt keeps its `promptId` (answers remain fenced correctly) but carries a
  fresh `seq`; backfilled log entries keep their **original** `seq` — after a resume, treat the
  keyframe's `seq` as the new baseline and take backfill entries as history, not a gap.
- Lost token / new device: `lobby.join` name re-bind (§5) triggers the same keyframe + prompt +
  backfill sequence under the caller's fresh token.
- Commands are idempotent by `id`: the bridge remembers recent command ids per session (LRU of
  64) and re-sends the recorded reply (`ack` or `error`) without re-executing — covers client
  retry after an ack was lost mid-drop. A duplicate arriving while the original is still
  executing is dropped (the original's reply is coming).
- **Post-game teardown:** a finished game stays resumable — and its chat open — for a grace
  period (default 15 min) after `game.over`; resuming it replays the final keyframe and
  `game.over` instead of a pending prompt. After teardown the bridge forgets the game: `resume`
  → `RESUME_FAILED`, game commands → `UNKNOWN_GAME`.
- Bridge process death loses the game in v1 (XMage does support client reconnection to a running
  game, so bridge-restart re-attach is a possible v2).
